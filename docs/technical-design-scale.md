# 技術設計：規模と操作量（案、2026-10-03）

企画書の「AIによって人間の操作限界を取り払う」を、ゲームの規模として作るための設計です。オーナー決定（2026-10-03）の順番は次のとおりです。

1. 操作量の物差しを決める
2. 試合の規模を上げる
3. 方針の出し方（分担）を整える

ゲームの中に会話する AI を入れるのは、この後です。3は、会話する AI の受け口にもなります。

この文書は `docs/technical-design.md`（Ver.1）と `docs/technical-design-v3.md` の契約に足すものです。矛盾したら、そちらを優先します。

---

## 0. 今の規模（2026-10-03）

| 項目 | 今の値 |
|---|---|
| マップ | 256m×128m（2m のマス、128×64） |
| コア | 1陣営1つ |
| 前線の拠点 | 2つ |
| 人口の上限 | 60（村人と兵の合計。`EconomyRules.PopulationCap`） |
| 開始時の兵 | 40体（両陣営の合計） |
| ベルト | 1陣営200マスまで |
| 処理の重さ | 480体で 1tick 約10〜12ms（予算は 50ms＝20Hz）。重いのは正規状態の書き出しとハッシュ |

この規模なら、人の手でほぼ回せます。

## 1. 操作量の物差し（S-1）

### 1.1 何を数えるか
「プレイヤーが手を入れたくなる場面」を、試合の中の出来事として数えます。お任せ同士の試合を Headless で流し、1分（1200tick）ごとの数を出します。

| 種類 | 出来事の例 |
|---|---|
| 内政：人 | 村人が手持ち無沙汰になった、資源点が尽きて村人が移った |
| 内政：建物 | 建物が完成した、訓練・研究が終わった（次を選ぶ場面）、人口の上限に達した |
| 内政：ライン | ラインが詰まった・切られた、加工の建物が材料待ちで止まった |
| 戦闘 | 敵を新しく見つけた、部隊の HP が半分を切った、拠点の持ち主が変わった、コアが攻撃された |
| 時代・文明 | 時代を進められるようになった |

あわせて、同時に動いているものの数（建物、ライン、部隊、戦線＝敵と接している拠点・道の数）も数えます。

### 1.2 目安
- 人がこなせる意味のある判断は、1分あたり **20〜40** ほどと見ています（上手な人の操作回数は1分に100〜200ですが、意味のある判断はその一部です）。
- 目標の曲線：
  - 序盤（0〜5分）：1分あたり **20前後**。人が全部こなせる
  - 中盤（10分ごろ）：**60以上**。半分くらいは AI に任せないと回らない
  - 終盤（15分以降）：**120以上**。分担なしでは回らない
- 今の規模の値を最初に測り、目標との差を2の規模の設計に使います。

### 1.3 作り方
- シミュレーションの中には何も足しません。数えるのは観測用の道具（`Simulation.PhaseHashObserver` と同じく、通常の試合では何も計算しない形）、または Headless の CLI のサブコマンド（`load`）にします。
- 状態ハッシュ・正規状態・挙動を変えないことを、テストで示します。
- 出力は分ごとの表（CSV）です。種をいくつか流して、平均とばらつきを出します。

## 2. 試合の規模を上げる（S-2〜S-4）

新しい規模は、**新しい地図の版（`mapgen-4`）と旗で切り替えます**。今の地図（mapgen-1〜3）のバイト列・挙動・テストは変えません。

### 2.1 目標の値（案）

| 項目 | 今 | 目標（案） |
|---|---|---|
| マップ | 256×128m | **512×256m**（マスは2mのまま、256×128） |
| 前線の拠点 | 2 | **6〜8**（真ん中の帯と左右の縁に散らす） |
| 資源地 | コアのまわり＋散らばり | 地図のあちこちに**資源の固まり**を置く（遠征して取りに行く価値を作る） |
| 人口の上限 | 60 | **200**（住居で上げる。兵は最大で150前後） |
| 自分の町 | コア1つ | コア＋**支城（新しい建物）を2〜3**。支城は資源の受け取り・村人の訓練・近くの建物の建設の拠点になる |
| ライン | 数本 | 加工の連鎖を複数の町で組むので、**数十本** |

数字は案です。S-1の物差しで、1.2の曲線に近づくように決め直します。

### 2.2 段階（それぞれ Codex に発注）
- **S-2 地図の拡大**：`mapgen-4`（512×256、拠点6〜8、資源の固まり）。決定論と公平さの規則（コアの近くに最低限の資源）は今と同じです。重さは 2 倍のマス数で測ります（経路探索・視界の計算が増える）。
- **S-3 支城**：新しい建物 `Outpost Town`（仮の名前）。村人の訓練・資源の受け取り・時代に関係しない内政の拠点にします。お任せは、資源の固まりのそばに支城を建てます。Contracts に建物の値を1つ足します（告知は Issue #135）。
- **S-4 人口と兵の数**：人口の上限を200に上げ、兵の訓練・お任せの軍の編成が150体前後で回るか確かめます。重さを測ります（目安は 1tick 50ms 以内。正規状態の書き出しが重ければ、記録の間隔の見直しを別に考える）。

### 2.2.1 S-1・S-2 の測定でわかったこと（2026-10-03）
- **地図を大きくしても、操作量は増えなかった**（mapgen-3 → mapgen-4 で1陣営1分あたり 15.6 → 12.1。戦線は 0.30 → 0.42）。重さは平均 2.8ms・p99 11ms で問題ない
- **部隊は試合を通して4つのまま**。1陣営の部隊は北16・南16・予備6・斥候2の定員で、**合計40が兵の数の上限**になっている（`Simulation.Reinforcements.cs`：定員に空きのある部隊がなければ兵を生み出さない）。人口の上限を上げても兵は増えない
- 「集中」の早攻めだと、5分までにほとんどの試合が決着する。方針なし同士は戦いが散発するだけ
- オーナー決定（10-03）：**同時に動かすものの数を増やす**方向で進める。早攻めは、お任せの判断を変えるのではなく、**コアに攻撃を持たせて序盤に簡単に落ちないようにする**（時代と結びつけない常設の守り）

### 2.2.2 部隊の自動増設（S-4 を置き換える）
- 旗：`EconomyRules.ArmyGrowth`（仮の名前、既定オフ）
- **すべての部隊が定員に達していて、兵を新しく生み出すとき、新しい部隊を作る**。新しい部隊の役割は「野戦」（`Role = "field"`、仮）、定員は【12】
- 新しい部隊の受け持ち（`HomeObjective`）：自陣から近い順に、まだどの部隊も受け持っていない拠点。なければコア
- 上限：1陣営【12】部隊まで（兵の数で言えば 40＋8×12＝136 前後）。人口の上限も合わせて上げる（【200】）
- 部隊の ID は試合の中で増える（今は試合の初めに決まった数で固定。`NextArmyId` を増やせるようにする）。部隊の並びは ID 順で、決定論を保つ
- お任せの軍の判断（`PolicyDecision`・`OffenseDecision`）は、もともと部隊の数に依らない作りなので、増えた部隊もそのまま割り当ての対象になる。判断の中に旗の分岐は足さない
- 表示に渡す部隊の一覧（`FactionObservation.OwnArmies`）は可変長なので、Contracts は変えずに済む見込み（変える場合は Issue #135 で告知）
- 旗オフでは、今までのバイト列・挙動を変えない

### 2.2.3 内政の規模（S-4b、部隊の自動増設の測定でわかったこと）
- 部隊の自動増設（`ArmyGrowth`）をオンにしても、部隊は4つのまま、兵は1陣営25〜28人で止まった（定員の合計40に届かない）
- 本当の頭打ちは内政：
  - **兵舎は1つだけ**（お任せは兵舎がないときにしか建てない。`EconomyDecision.ShouldBuildBarracks`）。兵を作れるのは常に兵舎1つ分
  - **村人の目標は20人**（地形の地図の `AutoVillagerTarget`）。稼ぎもそこで止まる
  - 人口の上限は、基本30＋住居1つにつき5
- 直し方（旗 `ArmyGrowth` がオンのときだけ。名前は `EconomyScale` に分けてもよい）：
  - 村人の目標を、時代に合わせて伸ばす：原始【20】→ 2つ目の時代【40】→ 3つ目の時代【60】
  - 兵舎を稼ぎに合わせて増やす：村人【15】人ごとに兵舎1つ（最大【4】）。訓練の待ちは兵舎ごと
  - 住居を人口の上限に合わせて建て続ける（今の住居の判断の上限を、人口の上限 200 まで伸ばす）
- 狙い：中盤（10分）で兵 60〜80、終盤で 100 以上。部隊が 6〜10 になり、同時に動かすものが増える

### 2.3 重さと決定論
- 数百体・数十本のライン・広い地図で、経路探索（`GridMap.FindPath`）、視界、正規状態の書き出しが重くなる見込みです。各段階で `bench`（`AllocKBPerTick`・処理ごとの ms）を測り、PR に書きます。
- `float`・`double`・`Dictionary` の列挙順を判定に使わないなど、決定論の決まりは今までどおりです。

## 3. 方針の出し方を整える（S-5）

人が「北は任せる、南は自分で」「町Aの内政は任せる、町Bは自分で」と分担できるようにします。会話する AI も、この同じ形で命令を出します。

- **担当の範囲**：「区域」（拠点・道・町）ごとに、担当を「AI」か「自分」に切り替えます。今の「人の操作が最優先」「AIに戻す」を、区域ごとに持たせる形です。
- **区域ごとの方針**：攻める・守る・内政を伸ばす・資源を取るなど。今の方針（`PolicyKind`、内政の方針）を区域に結びつけます。
- 命令は今までどおり `ICommandPort` 経由です。Contracts には、区域の ID と担当の切り替えの命令を足します（告知は Issue #135）。
- 表示（区域の担当の見え方、切り替えのボタン）は相方の担当なので、Issue で依頼します。

### 3.1 今あるもの（2026-10-03）
- 人が手で持っている印は、物ごとにあります。村人と建物は `PlayerHeld`、コアの内政は `CoreHeld`、ラインは手で引いたら「手動の管理」です。「AIに戻す」（`ReturnEconomyToAuto`・`ReturnLineToAuto`・`PolicyKind.ReturnToAuto`）で外します。
- 方針の命令の範囲は `ScopeKind`（`All`・`Army`・`Outpost`）の3つです。
- つまり、「ここから先はAI、ここは自分」を**場所のまとまり**で決める手段はまだありません。

### 3.2 区域の決め方
- **区域の中心**は、コア・支城（S-3）・前線の拠点です。地図の版（`mapgen-4`）で、各マスがどの区域に属するかを決めます。いちばん近い中心の区域にし、距離が同じなら中心の ID が小さい方にします（決定論）。
- 区域の ID は、試合の初めに決まる番号です。支城が建ったら、その区域を足します（ID は足した順）。
- 区域は**両方の陣営に共通**の地理です（拠点の取り合いをそのまま区域の取り合いにできる）。

### 3.3 担当（区域ごと・陣営ごと）
- 各陣営は、区域ごとに **担当＝AI か 自分** を持ちます。既定はすべて AI です。
- **自分の担当の区域では、お任せが新しく手を出しません**。その区域に新しく建物を置かない、そこにいる手の空いた村人に仕事を割り振らない、そこにいる部隊を勝手に呼び戻さない。すでに動いている仕事（建設中の建物、運んでいる荷物）は最後まで続けます。
- 個別の `PlayerHeld`・`CoreHeld` はそのまま残します。区域の担当は、それをまとめて切り替える上の層です（自分の担当の区域の物は、手で持っているものとして扱う）。
- 命令：`SetRegionControl(regionId, Human|Ai)` を足します。担当を AI に戻すと、その区域の物の `PlayerHeld` も外れます（今の「AIに戻す」と同じ）。

### 3.4 区域ごとの方針
- `ScopeKind` に **`Region`** を足し（追加だけ）、今の方針（`Focus`・`Defend`・`AllowAbandon` など）と内政の方針（`EconomyPolicy`）を、区域を範囲にして出せるようにします。
- 例：「北の区域を守る」「西の町は内政を伸ばす」「東の拠点は捨ててよい」。
- 会話する AI は、プレイヤーの言葉をこの「区域の担当」と「区域の方針」の命令に置き換えて出します（AI の埋め込みの段階で作る）。

### 3.5 決定論と記録
- 区域の分け方は地図から決まるので、記録には種があればよいです。担当と方針は命令として記録されます。
- 正規状態には、担当や方針が既定（AI・方針なし）から変わった区域だけを書きます（今の試合のバイト列を変えない）。

## 4. 進め方
- 実装は Codex に発注し、オーナー側の Claude が設計・レビュー・検証・マージを行います。
- 各段階は旗で切り替え、旗がオフなら今までと同じです。
- S-1 の物差しの最初の測定結果を見てから、2.1 の数字を決め直します（オーナーに報告します）。
