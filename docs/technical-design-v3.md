作成日：2026-09-22。根拠：企画書 3章（勝ち方のパターン・プレイヤーの関わり方・内政と生産・時代と文明・マップのランダム生成）と 15章（MVP Ver.3）。Ver.1 の契約（固定小数点、tick、乱数、ID、再生形式、決定論の検査）は `docs/technical-design.md` のとおりで、本書はそれに**足すもの**だけを書く。矛盾したら Ver.1 の契約を優先し、変える場合は本書で明示する。

## 1. V3-1 の範囲と完成条件

**作るもの**：種から作るマップ、資源2種、村人、建物1種（兵舎）、兵の生産、作った兵が今の戦闘に加わるところまで。両陣営に最小の内政のお任せAIを付ける（相手が何もしない試合にしないため）。

**作らないもの**（V3-2 以降）：加工の建物、物を運ぶライン、内政の方針指示、人の直接操作とAIの受け渡しの細かい規則、時代と文明、地形の種類（森・川・山の区別）、資源置き場、建物の修理、村人の反撃・逃走。

**完成条件（関門）**
1. 同じ種からは必ず同じマップになる。生成したマップはリプレイのヘッダーに入り、再生は生成し直さない
2. お任せ同士の試合が、複数の種で **36000 tick 以内にコア破壊で決着**し、Fault がない
3. 全tickのハッシュが、記録と再生で一致する（既存の決定論テストと同じ基準）
4. 生産した兵が軍団に入り、戦闘に参加する（ダンプで確かめる）
5. **既存のシナリオ（week1・week2・week3）は、決着tickが今と変わらない**（内政のないシナリオでは新しい処理が何もしない）

## 2. マップのランダム生成

### 2.1 置き場所と契約（確定）

- `Simulation/MapGenerator.cs`（純C#、Simulation アセンブリ）。**`Step` からは呼ばない。** 試合の前に1回呼んで `ScenarioDefinition` を返す
- 入力：`seed`（ulong）、生成器の版（`MapGeneratorVersion = "mapgen-1"`）、寸法。出力の `ScenarioId` は `"gen1-" + seed`
- 乱数は Ver.1 の SplitMix64（7章）。**整数だけ**で計算する。範囲の乱数は棄却法で偏りをなくす
- **リプレイは生成し直さない。** 生成結果の `ScenarioDefinition` を、今と同じくヘッダーに丸ごと入れる（13.1章の「マップを外部パス参照だけにしない」をそのまま満たす）。したがって、再生の決定論は生成器の実装に依存しない
- それでも生成器自体も決定論にする（同じ種・同じ版なら、どの環境でも同じバイト列）。将来のオンライン対戦で、両者が種から同じマップを作り、設定ハッシュ（`Config.Hash`）を突き合わせてから始めるため。テストで固定する
- 生成器の出力の意味を変えたら版を上げる（`mapgen-2`）

### 2.2 生成の手順（仮設定の値つき）

寸法は V3-1 では今と同じ **256×128 m・2 m 角のセル**（表示側の前提を崩さないため）。生成器は寸法を引数に取る。

1. **コアの位置**：西のコアは x∈[20,60]、東のコアは x∈[196,236]、z∈[20,108] から乱数で選ぶ。コア間の距離は 150 m 以上（満たさなければ引き直す）
2. **障害物**：矩形の塊を 6〜10 個、乱数の位置と大きさで置き、通行不可にする。通行不可の合計はマップの 20% 以下。**コアと拠点と保証資源の周囲 8 m には置かない**
3. **拠点2つ**：コアを結ぶ線の中点から、線に垂直な方向へ ±32 m（乱数で ±8 m ずらす）。z が大きい方を「北」、小さい方を「南」と呼ぶ（Ver.1 のお任せAIが北／南の2拠点を前提にしているため。9.2章）
4. **保証資源（公平さの規則）**：各コアから半径 12〜30 m の輪の中に、**木材の資源 4 つと食料の資源 3 つ**を必ず置く（位置は乱数）
5. **散らばる資源**：マップ全体に木材 16・食料 10 を乱数で置く。コアから 30 m 以内には置かない（保証資源と区別するため）
6. **つながりの検査**：西のコアのセルから塗りつぶし（4近傍、通行可能セル）をして、東のコア・2つの拠点・すべての保証資源に届くか確かめる。届かなければ**障害物だけを引き直す**（乱数の続きを使う。最大 64 回、超えたら生成失敗として例外）
7. 軍団・初期の兵・村人を置く（4章の初期状態）

**公平さについて（確定しない）**：V3-1 は「近くに最低限の資源がある」と「互いに到達できる」だけを保証する。距離・資源の総量の偏りは測るだけにとどめ、規則はV3-4 以降に決める（地形と文明の選択に効かせる設計と一緒に決めるため）。

### 2.3 資源の置き方（確定）

- 資源は**点**として持つ（`ResourceNodeDefinition { Id, Kind, Position, Amount }`）。**通行を妨げない**（木を障害物にしない。経路探索を変えないため）
- 資源の位置は、その資源があるセルの中心に置く（整数メートル）
- 同じセルに2つ置かない

## 3. データの追加

### 3.1 シナリオ（`ScenarioDefinition`）

| 追加 | 中身 |
|---|---|
| `ResourceNodes` | `ResourceNodeDefinition[]`：Id、Kind、Position、Amount（初期量） |
| `Economy` | `EconomyRules`：有効かどうか（`Enabled`）、初期の蓄え、人口の上限、各建物・各兵のコストと時間、採集の速さと運べる量、足跡の大きさ |
| `Villagers` | 初期の村人（`SoldierDefinition` と同じ形。Kind=Villager、ArmyId=0） |
| `Buildings` | 初期の建物（V3-1 は空。将来のシナリオ用） |

- `Economy.Enabled == false`（既存のシナリオすべて）なら、以下の新しい処理は**何もしない**。1章の関門5はこれで守る
- `ScenarioBinary` の形式を **schemaVersion 2** に上げ、上の項目を書く。**v1 の記録も読める**ようにする（無い項目は空・無効として読む）
- `RulesVersion` を上げる（`v3-economy-1`）

### 3.2 状態（`WorldState`）と正規状態のハッシュ

新しい配列と値はすべて正規状態に入れ、Ver.1 の順序規則（13.2章）に従う（ID昇順、宣言したフィールドを明示的に書く）。

| データ | 必須フィールド |
|---|---|
| FactionState に追加 | 蓄え（食料・木材、int）、人口（村人数・兵数）、人口の上限 |
| ResourceNodeState | Id、Kind、Position、Remaining（残量） |
| 村人の状態（SoldierState に追加） | Task（待機／資源へ移動／採集中／蓄えへ移動／建設へ移動／建設中）、対象ID、運搬中の種類と量、次の採集tick、個人の経路・カーソル |
| BuildingState | Id、FactionId、Kind、足跡の左下セル、Hp、建設の進み（0〜必要量）、完成したか、生産の列（兵の種類の並び、最大5）、今の生産の残りtick |

- 正規状態に節を足すため、**既存シナリオでもハッシュの値そのものは変わる**。関門は「挙動（決着tick・勝敗）が変わらないこと」で見る。ハッシュの値を固定しているテストはない（確認済み：`PhaseDiffTests` の定数は比較用の架空の値）
- 建物で通行不可になったセルの一覧は、建物の配列から毎回作り直せるので、**正規状態に入れない**（キャッシュ扱い。13.2章「除外したキャッシュは同一手順で再生成できることをテストする」に従う）

### 3.3 共通の型（Contracts）の変更

以下は Contracts の変更なので、**相方への告知 Issue を作る**（CLAUDE.md ルール7、ラベル `B: 表示・UI`・`共同`）。相方は現在PCを触らないため、告知だけ作り、返事は待たない（オーナー判断 2026-09-21 の連絡保留に従う）。

- `UnitKind.Villager = 4`（3 は保留中の PR #62 の守衛が使っているため空ける）
- `ResourceKind : byte { Food = 1, Wood = 2 }`
- `BuildingKind : byte { Barracks = 1 }`（コアは既存の Core のまま。建物に含めない）
- `InputKind.Economy = 5`：内政の直接操作（6章）
- `FactionFrame` に追加：蓄え、人口と上限、自分の建物（生産の列を含む）、見えている敵の建物、資源（位置・種類・残量）、村人（自軍の兵と同じ形で、Kind で区別）
- `EnemyContact` に `IsNonCombatant`（村人。敵の兵力の推定に数えないため。5章）
- `ICommandPort` に内政の操作を送るメソッドを追加（6章）

## 5. シミュレーションの処理

### 5.1 tick の処理順（Ver.1 の6章に差し込む）

| 順 | 処理 | 追加・変更 |
|---|---|---|
| 1 | 確定入力の適用 | **内政の操作**を適用する（建物の配置、生産の予約・取消）。コストはこの時点で引く。足りなければ拒否して記録 |
| 2 | AI | 内政のお任せAI（5.4）を t%20=0 で実行。**村人の行動の決定**（5.3）は毎tick |
| 3 | 経路・移動 | 村人も移動する。村人は**1人ずつ経路を持つ**（下の 5.2） |
| 4 | 攻撃 | 兵は、見えている敵の村人と建物も狙える（コアと同じ判定で、建物は足跡の矩形までの距離で測る） |
| 5 | 死亡 | 村人の死亡、建物の破壊（HP≤0）。破壊された建物のセルは次のtickから通行可能 |
| **5.5** | **内政**（新） | ①採集：採集中の村人が期日に1単位取る（残量から引く）②納品：蓄えへ移動していた村人がコアに届いたら蓄えに足す ③建設：建設中の村人の数だけ進める。完成したら生産を受け付ける ④生産：列の先頭の残りtickを1減らし、0なら兵・村人を出す。**出た兵は当tickに動かない**（増援と同じ規則） |
| 6〜10 | 占領・増援・視界・終了・出力 | 変更なし。増援は内政ありのシナリオでは無効 |

同じtickの中の順序は、陣営ID→建物ID／村人ID昇順（Ver.1 の同点解決に従う）。

### 5.2 経路探索の変更（確定）

- **地形が変わるようになる。** 今の `GridMap.FindPath` のキャッシュは「地形は変わらない」前提の純関数（`GridMap.cs` 17行目のコメント）。建物の完成・破壊で通行可能セルが変わったら、**キャッシュを全部捨てる**。捨てる時点は処理順5・5.5 の終わりで、同じ入力なら同じtickに捨てるので決定論は保たれる。キャッシュの有無で結果が変わらないことをテストで固定する
- 建物の配置は、**建設を始めた時点で**足跡のセルを通行不可にする（建設中に兵が中を通らないため）
- Ver.1 は「兵士ごとの A* はしない」（6章）。**村人は例外**として1人ずつ経路を持つ（行き先がばらばらのため）。人数は人口の上限で抑えられ、キャッシュが効く。重さは `bench` で測る
- 建物の足跡の上に兵や村人が残っていたら、足跡の外の最寄りの通行可能セルへ移す（距離→セルIDの順。Ver.1 の増援の出現位置と同じ規則）

### 5.3 村人の行動（確定）

状態機械：待機 → 資源へ移動 → 採集中 → 蓄えへ移動 → （納品）→ 資源へ移動 …、建設を割り当てられたら 建設へ移動 → 建設中 → （完成）→ 待機。

- 採集中：20 tick ごとに1単位。運べる量（10）に達するか資源が尽きたら蓄えへ移動
- 資源が尽きたら、同じ種類で最も近い資源（距離→ID）へ移る。30 m 以内に無ければ待機
- 納品先は自分のコア（V3-1。資源置き場は作らない）。コアの半径＋2 m に入ったら納品
- 待機中の村人は、内政のお任せAIが割り当てる（5.4）。人が直接割り当てた村人も同じ状態機械で動く
- **テストは、この一巡（移動→採集10回→移動→納品→次の採集）をまたぐ長さで回す**（前アカウントの教訓：1tick だけのテストは状態機械の罠を見逃した）

### 5.4 内政のお任せAI（最小、Decision）

Decision に置き、**自陣営の観測だけ**を入力にする（Ver.1 ルール6）。自陣営の蓄え・建物・村人は、自分の情報なので観測に全部入る。資源の位置と残量は、V3-1 では**地形と同じく双方に公開**とする（霧で隠すのは V3-2 以降の判断）。

t%20=0 で、次の順に1つずつ判断して、内政の操作を提案する（人の操作と同じ入力の形で記録する）。

1. 村人が目標（10人）未満で、コアの列が空で、食料が足りれば、村人を1人作る
2. 兵舎がなく、木材が足りれば、兵舎を置く。置き場所は「コアから最も近い、足跡の全セルが通行可能で、コア・資源・他の建物から 2 セル以上離れた場所」。探す順は、コアのセルを中心にした渦巻きの順（決定論にするため、順番を固定する）
3. 完成した兵舎があり、列が 2 未満で、コストが足りて、人口に空きがあれば、歩兵を1人作る
4. 待機中の村人を、**蓄えの少ない方**の資源（食料：木材の目標比 2:1 で比べる）の、最も近い資源へ割り当てる

人の陣営でも、V3-1 では「内政のお任せ」を**既定で入れる**（入り切りできる）。人が直接操作した分はそのまま通り、お任せAIはその結果の状態を見て次を判断する。**人が触った所からAIが手を引く規則は V3-3 で作る**（V3-1 では、両方が同じものを作ろうとして二重になることがある）。

### 5.5 既存の戦闘AIとの関係（確定。守衛の教訓）

前アカウントで守衛（速度0の兵）を足したとき、新しい種類の兵が既存のAIの前提を複数の箇所で壊した（追撃の罠、人数の数え方、兵力の推定、増援の割り当て）。村人でも同じことが起きうるので、**触る箇所を先に列挙する**。

| 箇所 | 村人の扱い |
|---|---|
| 軍団（Army） | 村人は軍団に入らない（ArmyId=0）。軍団の配分・攻勢・撤退・追撃の対象外 |
| 陣営の人数（`AliveCount`） | **兵だけ**を数える（今の意味を変えない）。村人は別に数える |
| 敵の兵力の推定（`EnemyStrengthEstimate`・`CountableContacts`） | `IsNonCombatant` の接触を数えない |
| 危機の判定（9.2章 手順1） | 自コアの近くに来た敵の村人では、危機にしない（非戦闘員を除く） |
| 生産した歩兵の軍団への割り当て | Ver.1 の増援の割り当て（`Simulation.Reinforcements`）をそのまま使う。発生点は兵舎で、兵舎を HomeObjective に持つ軍団はないので、予備→残る歩兵軍団のID順になる |
| 標的の選択 | 兵は敵の村人・建物も狙う。優先はVer.1の順（兵士→コア→拠点）に村人・建物を足す：兵士→村人→建物→コア→拠点 |

## 6. 内政の直接操作（入力）

人の直接操作は、方針（`UserPolicyIntent`）とは別の入力として送る。

- `EconomyCommand { Faction, Sequence, Kind, … }`。Kind は V3-1 では次の4つ
  - `PlaceBuilding(BuildingKind, 足跡の左下セル)`
  - `Train(BuildingId or CoreId, UnitKind)`
  - `CancelTrain(BuildingId or CoreId, 列の位置)`：コストは返す
  - `AssignVillagers(村人ID の一覧, 対象)`：対象は資源か建設中の建物
- ゲートウェイが受け付け順を決め、`InputKind.Economy` として記録する（LogIndex の規則は Ver.1 と同じ）。**方針の命令と違い、翻訳・AIの遅延を通さない**（定型命令で遅延0を選んだときと同じく、次のtickに適用）
- 適用時に検証する：自陣営のものか、コストが足りるか、足跡がすべて通行可能か、列に空きがあるか。通らなければ拒否し、拒否の理由も記録する（再生で同じ結果になるように）

## 7. 表示（Presentation・UnityHost）

表示は相方の担当範囲だが、相方がPCを触らない間はオーナー側が実装する（2026-09-19 からの運用と同じ）。

- 試合の開始時に種を決めてマップを作る。**種は画面に出す**（同じマップでもう一度遊べるように）。種の決め方は試合の外（UnityHost）なので、ここでだけ時計を使ってよい（シミュレーションの判定には入らない。生成結果はリプレイに入る）
- 表示するもの：資源（種類ごとの仮モデル）、村人、建物（建設中は半透明など）、蓄えと人口
- 操作：兵舎の配置（地面をクリック、置けない所は赤）、コア・兵舎での生産ボタンと列、村人を選んで資源をクリックで割り当て、「内政のお任せ」の入り切り
- 相手の方針の選択（PR #132）は残す。内政ありの試合では、敵の軍団はお任せの戦闘AI＋内政のお任せAIで動く

## 11. ベルトの表し方（確定）

### 11.1 1個ずつの物として持つ

**ベルトの上の物は、1個ずつ持つ**（流量では持たない）。

- 理由：①「どこで詰まっているか」が画面にそのまま見え、ラインの設計の良し悪しが目で分かる（企画の面白さの芯）②合流・詰まり・途中で壊されたときの挙動が、流量だと別の規則が要るが、1個ずつなら同じ規則で済む ③整数だけで書け、決定論が保ちやすい
- 重さ：ベルト1セルに物は**最大1個**。ベルトのセル数は陣営あたり上限（仮設定 200）。1tick の処理はベルトのセル数に比例し、`bench` で測る

### 11.2 データ

| データ | 必須フィールド |
|---|---|
| BeltState（新しい配列。セルID昇順） | セルID、陣営、向き（北・東・南・西）、HP、載っている物の種類（無しは0）、物がこのセルに入ってからのtick数 |
| 建物の入口・出口 | 採掘場・精錬所は**向き**を持つ。出口は「向きの側の辺の中央の、足跡のすぐ外のセル」。入口は足跡のどのセルでもよい（ベルトの行き先が足跡の中なら入口） |

- ベルトは**通行を妨げない**（兵も村人も上を歩ける。経路探索を変えないため。資源の点と同じ扱い）
- ベルトを置けるのは、通行可能で、建物の足跡・コアの半径・資源の点・他のベルトと重ならないセル
- ベルトの処理順（下の 11.3）は、ベルトの並びから毎回作り直せるので正規状態に入れない（キャッシュ。置く・壊すで作り直す。キャッシュの有無で同じ結果になることをテストする）

### 11.3 物の進み方（1tick）

1. **処理順を決める**：各ベルトの「終点までの距離」（行き先をたどって、建物の入口・コア・ベルトでない所に着くまでのセル数）を求め、**距離の小さい順→セルID昇順**に並べる。輪になったベルトは距離を最大として最後に回す（輪でも決定論は保たれる）
2. その順に、載っている物のtick数を1足す。**BeltTicksPerCell（仮設定 8 tick）** に達していて、行き先が受け取れるなら渡す
   - 行き先がベルト：そのセルが空なら載せる（tick数は0から）
   - 行き先が建物の入口：その建物がその種類を受け取り、入口の置き場に空きがあれば渡す
   - 行き先がコア：自陣営のコアなら蓄えに足す
   - それ以外（何もない地面・敵のもの）：動かない（詰まる）
3. 下流から先に処理するので、詰まっていない列は隙間なく流れる。**2本が1つに合流するとき**は、処理順で先のベルト（距離→セルID）が先に入る
4. 建物の出口：採掘場・精錬所の出口の置き場に物があり、出口のセルに自陣営の空いたベルトがあれば、1個載せる（ベルトの処理の後）

処理は 5.1 の内政の段の中、①採集の前に置く（段の数と名前は変えない。8.1 と同じ理由）。

### 11.4 壊れたとき

- ベルトが壊れたら、載っていた物は失われる。セルは空く（通行は元から妨げていない）
- 採掘場・精錬所が壊れたら、置き場の中身は失われる。足跡は通れるように戻し、経路を作り直す（兵舎と同じ）

手運びが無いと関門1の比べる相手が無く、ラインを組む前の序盤も回らないので、V3-2 で入れる。

- mapgen-1 の試合は金属コスト 0 のまま（10章の関門4）

## 13. お任せ内政AIの追加（Decision）

V3-1 の手順（5.4）の3と4の間に足す。

1. 採掘場がなく、木材が足りれば、**自コアに最も近い鉱石の資源**（距離→ID）に採掘場を置く
2. 精錬所がなく、木材が足りれば、採掘場とコアの間に精錬所を置く（置き場所の探し方は兵舎と同じ渦巻き。採掘場とコアの中点から探す）
3. 両方が完成したら、**決まった形のライン**を引く：採掘場の出口→精錬所の入口、精錬所の出口→コア。道筋は、ベルトを置ける セルだけを通る4近傍の最短路（同じ長さならセルID の小さい方へ曲がる、で固定）。木材が足りない間は、足りた分から順に置く
4. ラインが無い間（または途中が壊れている間）は、村人を2人運搬に回す

**人の直接操作との関係**：V3-1 と同じく、お任せを切れば AI は何も置かない。人が引いたラインをAIが避ける・直す規則は V3-3。

## 19. 人の預かり（確定）

戦闘の「人の命令はお任せAIより優先」と同じ考えを、内政の物ごとに持つ。**預かりの印は、Industry のマップ（mapgen-2）でだけ付ける**（V3-1 のマップの挙動と正規状態を変えないため）。

| 物 | 人の預かりになる操作 | お任せの内政がしなくなること | 預かりが外れるとき |
|---|---|---|---|
| 村人 | `AssignVillagers`（採集・建設・手運び） | 待機になっても割り当てない。建設の人手・手運びの人手に選ばない | お任せに戻す。村人が死ぬ |

- 「お任せ内政の入り切り」（V3-1）はそのまま残す。切ると預かりに関係なく何もしない
- 預かりは正規状態に入れる（村人・建物・ベルトごとの印と、コアの印）

## 20. 内政の方針（仮設定）

|---|---|---|---|---|

## 28. 地形とマップ（mapgen-3）

### 28.1 地形の種類（確定）

セルごとに地形の種類を持つ（`MapDefinition.Terrain`、セル数の byte 列。空なら全部平地）。**通れるかどうかは今までどおり `BlockedCellIds` が正**で、地形の種類はそれに意味（何が近くにあるか、見た目）を足すだけにする。移動の速さも経路探索も変えない（Ver.1 の経路・移動の規則をそのまま使うため）。

| 種類 | 通れるか | 近くにある資源 | 文明への効き目 |
|---|---|---|---|
| 平地（0） | 通れる | — | — |
| 森（1） | 通れない（木が密） | **木材の点が森の縁に並ぶ** | どちらにも木材 |
| 川（2） | 通れない。**浅瀬**（平地のセル）でだけ渡れる | **食料の点（魚・肥えた土）が岸に並ぶ** | 農耕：農場は川に近いほど速い |
| 山（3） | 通れない | **鉱石の点が山のふもとに並ぶ** | 冶金：鉱石が多い |

### 28.2 生成（仮設定）

mapgen-1 の矩形の障害物の代わりに、地形を置く（**新しい版 mapgen-3**。mapgen-1・mapgen-2 は今のまま作れるよう残す）。

1. コア・拠点：mapgen-1 と同じ引き方
2. **川**：マップを南北に横切る川を1本（幅2セル、x は 90〜166 m の間を左右に揺れる）。**浅瀬を3〜4か所**（幅4セル）開ける。拠点の近くには必ず浅瀬を1つ
3. **山**：塊を 3〜5 個。**森**：塊を 5〜8 個（楕円に近い形、整数だけで作る）
4. **コアの周りの寄り**：各コアについて「山寄り」か「川寄り」かを乱数で決める（左右で揃えない）。山寄りならコアから 20〜36 m に山の塊を1つ、川寄りなら 16〜30 m に池（川と同じ種類の小さな塊）を1つ置く
5. 資源：保証資源（V3-1 の食料・木材）に加え、森の縁に木材、川岸に食料、山のふもとに鉱石を並べる
6. つながりの検査（V3-1 と同じ。届かなければ地形を引き直す）

- 地形が通れない割合の合計は、マップの 25% 以下
- 公平さの規則は測るだけ（V3-1 と同じ）

### 28.3 見た目

地形の色：平地は緑、森は濃い緑、川は青、山は灰色（今の仮素材の色分け）。

### 32.1 作り方の決まりごと

- 新しい要素は**時代のあるマップ（mapgen-3 以降）でだけ**効かせる。Ver.1・V3-1〜V3-3 のマップは挙動も正規状態も変えない

- 新しい兵種は、戦闘AIの前提（兵の種類で分ける箇所）を先に列挙してから足す（守衛の教訓、5.5）
- 数の詰めはしない。一通り動き、お任せ同士の試合が決着することを確かめる

### 32.15 実装で決めたこと（#15 修理）

### 32.23 釣り合いの調査（冶金が弱い件、#20時点）

オーナーの指示で、これまで「測って報告で止める」としてきた冶金の弱さに実際に手を入れてみた。結論は**見送り**（変更は取り消した）。過程を残す。

| 項目 | 内容 |
|---|---|
| 測定（8種、12000 tick、文明ごとの強さ） | 農耕7勝・冶金1勝（種1のみ冶金）。種7 は農耕28000に対し冶金9460と大差 |
| 種7 の内政推移 | 12000 tick の間ずっと食料0〜40のまま、木材182・金属122まで積み上がる。兵の数は22〜25で頭打ち（人口の上限35〜40には余裕があるのに）。**食料だけが詰まっている** |
| 試した直し | 木材の床（32.11）と対になる「食料が150未満かつ木材より少なければ食料へ」を**冶金の文明だけ**に絞って追加（前回、両文明に効かせて農耕がさらに伸びた反省を踏まえた） |
| 効かなかった理由 | 村人の活動を tick ごとに見ると、**「待機」が一度も出ない**（ずっと移動中・採集中・帰還中を巡回）。今の割り当て（`AssignWork`）は村人が**待機になった瞬間**にしか呼ばれないので、既に働いている村人は食料が枯渇しても割り当てを見直さない。冶金は村人の総数が7〜10人と少なく、新しく生まれる村人も少ないので、割り当ての基準を変えても実際に動く場面がほとんど無かった |
| 測った効果 | 冶金の勝ち数は 2→1 に**悪化**（種3 が冶金勝ちから農耕勝ちに変わった）。木材の床のときのような改善は無く、むしろ雑音になった。**変更は取り消した** |
| 本当に直すには | 「食料が枯渇したら、既に働いている村人の一部を食料へ回す」という、待機を待たない割り込みが要る。これは`AssignWork`の呼び出し方そのものを変える必要があり、今晩の他の直し（床の追加）より大きい変更になる。次に取り組むならここから |

### 32.24 実装で決めたこと（#22 僧侶・改宗）

企画書・これまでの技術設計に記述のない完全新規機能。**兵士個体の`FactionId`は一切書き換えない**という方針で設計した（下記「検討した理由」参照）。芯に関わる決定のため、実装発注前にAstraへレビューを依頼した。

| 箇所 | 実装した形と理由 |
|---|---|
| 僧侶 | 新しい兵種 `UnitKind.Monk = 9`。**兵舎で**訓練できる（斥候と同じ建物）。`EconomyRules.MonksEnabled`（既定 `false`）が true の時だけ訓練可能。旗が false のときは1バイトも挙動を変えない（32.1 の決まりどおり） |
| 相性 | **三すくみの対象外**（破城槌・斥候・傭兵と同じ扱い）。`CombatMath.Line()` にMonkを組み込んでいない（守衛の教訓を厳守） |
| 改宗の仕組み（検討した理由） | 兵士個体の`FactionId`は「生成時に決まる不変の値」として、Simulation層全体（標的選択・視界・接触記憶・軍編成・陣営上限など30〜40箇所）の前提になっている。これを書き換える方式は決定論・観測・リプレイへの波及が大きいため、**採らなかった**。代わりに「対象を通常の死亡として除去し、改宗した側の兵士を新規生成する」方式にした。これは訓練完了・増援で使われている既存の`Spawn`＋`ApplyClass`の組み合わせをそのまま再利用でき、既存のFactionId比較箇所に一切手を入れずに済む |
| 進捗の持ち方 | 対象兵士（`SoldierState`）に、シリアライズされない実行時専用のフィールド（改宗の進捗・仕掛けている陣営・最後に攻撃を受けたtick）を持たせた。同じ僧侶の陣営から連続して狙われている間だけ進捗が増える。1tickでも狙われなければ翌tickに進捗はリセットされる。複数の僧侶が同じ対象を同時に狙っても、1tickにつき進捗は1しか進まない |
| 改宗の完了 | `Attack()` の直後・`ResolveDeaths()` の直前に新しい `ResolveConversions()` を挟んだ。進捗が `ConversionTicks`（既定400tick）に達したら、対象のHpを0にして（既存の死亡処理に処理を委ねる）、改宗した陣営に**元と同じ兵種**の新しい兵士を、対象がいた位置に生成する（HP・状態異常・攻撃硬直は引き継がない。生まれたばかりの個体として扱う） |
| 陣営の人口上限 | 新規生成は既存の`Spawn`をそのまま使うため、`FactionCap`（陣営の人口上限）を自動的に守る。上限に達している場合は対象が死ぬだけで新兵士は生成されない（改宗の「不発」。エラーにはしない） |
| 対象外 | 僧侶同士・村人・建物は改宗の対象にならない（通常の敵兵士のみ） |
| テスト | `MonkConversionTests.cs`：既定オフでは改宗が起きない、連続接触で改宗が成立し元と同じ兵種で生まれる、僧侶を倒すと進捗がリセットされる、陣営の人口上限で改宗が不発になる、僧侶同士は改宗できない、リプレイ一致 |
| 実装元 | 発注文どおり Codex（`gpt-5.6-luna`、effort high）に発注。レビューで実装ロジック（`ResolveConversions`の兵種の引き継ぎ方が既存の訓練完了パターンと一致していること）を確認し、問題点は見つからなかった |

### 32.26 お任せの不具合の直し（撤退・村人・移動、2026-09-26〜28）

| お任せ | 冶金の2つ目の時代に入り、コア行きの金属のラインがそろったら、鋼がコアに届くまでの**一式**を組む（AI の1回の判断で1段ずつ。木材が足りなければその段で待つ）。鋼が2以上あれば、兵舎は歩兵の代わりに重装歩兵を作る（文明の特別な兵の「3人に1人」より先に見る） | 途中まででは、任せる価値が測れない |
| 人が手を入れたライン | ラインごとに管理者を持つ（`LineManager`：Automatic／Manual）。人がそのラインの建物・ベルトを建てる・回す・撤去する・運び手を割り当てると、**そのラインは手動の管理になり、AIは上書きしない**（建て直しも別の道での作り直しもしない）。`ReturnLineToAuto` で明示的にお任せに戻す | 企画書の3段（人の操作が最優先） |
| 敵に壊されたとき | 手動の管理にはしない。お任せのラインなら、お任せが作り直す | 壊されたのは人の判断ではない |
| （テストで見つけたこと） | 歩兵の攻撃の間隔（20tick）とお任せの判断の周期（20tick）がそろうため、**ベルトは叩かれたのと同じ tick に作り直されるとみられ、状態には一度も「消えた」と出ない**（攻撃は20tickごとに入っているが、6000tick見てもベルトは消えなかった。間隔を13にすると消えるのが見え、そのあと作り直された）。失うのは載っていた物と、作り直しの木材1だけ。お任せのラインは、事実上ベルトを切られない。テスト（`EnemyDestructionDoesNotHandAnAutomaticLineToThePlayer`）は攻撃の間隔を13にして観測している。本体は変えていない。襲撃の効き目の問題として、釣り合いの段で扱う | 実測 2026-09-29 |
| 時期 | 2つ目の時代に入る条件にも、3つ目の時代の値段にも鋼は入れない | 冶金が2つ目の時代に届かない問題（Issue #193）を先に片付ける |

### 32.30 ベルト部品と倉庫（V3-7）

#### 契約

`EconomyRules.BeltComponents` が `false` の場合、従来の通常ベルトの契約・処理・ハッシュは変更しない。現在の地形マップ（`MapGenerator.GenerateTerrain`）だけがこの旗を `true` にする。シミュレーション層は `UnityEngine` に依存しない。

`BeltComponentKind` は `None`、`Splitter`、`Sorter`、`UndergroundEntrance`、`UndergroundExit`、速度は `Normal`、`Fast` とする。`BuildingKind.Storage` は建物契約に追加する。配置コマンドは部品の種類、向き、必要なら地下入口・出口の2セルをリプレイに記録する。

#### 処理規則

| 部品 | 規則 | 初期値 |
|---|---|---:|
| 高速ベルト | 時代条件を満たす場合だけ置け、通常ベルトより短いセル時間で進む | `Age >= 2`、4 tick/セル、木材2/セル |
| 分岐器 | 正面を先に選び、詰まっていれば左を選ぶ。成功した搬送ごとに選択を交替する | 木材5 |
| 仕分け器 | 指定資源だけ左へ、それ以外は正面へ送る | 木材7 |
| 地下ベルト | 同じ向きの1〜4セル先へ一組で接続し、中間セルを見ずに出口へ送る | 木材3/組 |
| 倉庫 | 建物として建設し、1種類の資源を最大100個保持する。搬入・搬出は通常の手運びとベルトから行う | 2x2、木材120、HP700、建設300 |

ベルトは従来どおり1セル1個で、処理順は終端側からセル番号順の決定的な順序とする。部品の分岐先選択、地下の接続、倉庫の在庫、速度による進捗は正規状態に含め、`EconomyView`、診断ハッシュ、設計図、リプレイに同じ値を出す。無効な配置は資源・地形・状態を変更しない。

#### お任せ内政AIの金属・鋼ライン

`BeltComponents` が `true` の地形では、コア行きの `CoreMetal` ラインが建物・ベルトとも完成した後に鋼ラインを始める場合、まず専用の鉱山・精錬所を増設せず、精錬所の出口セルを分岐器に置き換える構成を固定順で試す。分岐器の正面側をコア、左側を製鋼所の金属入口とし、既存ラインを含む地形上の経路を北・東・南・西の順、各経路を幅優先で探索する。分岐器、必要なベルト、炭焼き小屋からの木炭線、製鋼所からコアまでの線を木材とベルト上限の範囲で一度に置ける場合だけ採用する。採用できない場合（地形、手動ベルト、木材、上限）は専用の鉱山・精錬所を使う従来構成へ戻る。

共有した鉱山・精錬所、分岐器、両方のラインに記録された共有ベルトのいずれかを人が編集した場合、コア金属ラインと鋼ラインの両方を `LineManager.Manual` とする。片方への「お任せに戻す」は共有単位の両方を `Automatic` に戻す。`BeltComponents` が `false` のマップではこの選択を行わず、従来の専用ラインの配置・ハッシュを保つ。地下ベルトはこの自動構成ではまだ選ばず、川や他ラインを越えられず共有構成を置けない場合も専用構成へ戻る。

#### UI・設計図

通常・高速ベルト、分岐器、仕分け器、地下入口/出口、倉庫を build 操作とツールキット操作から選べる。選択中の部品、向き、地下の仮接続は表示層だけで表現し、シミュレーションへは確定したコマンドを送る。ベルト部品を含む設計図 JSON は version 2 とし、version 1 は既定値（通常ベルト、部品なし）へアップグレードして読み込む。

#### 検証

部品の交替・詰まり時の分岐、資源別仕分け、地下の接続長、倉庫の容量、速度差、旗オフ時の互換性、シナリオ/リプレイのラウンドトリップを `Belt`、`Economy`、`Processing`、`Determinism`、`Replay`、`Scenario` のフィルターで検証する。ビルドとテストには `-p:NuGetAudit=false -p:UseSharedCompilation=false -nodeReuse:false` を付ける。

### 32.31 内政のライン依頼（V3-6 follow-up）

#### 命令の形

`EconomyCommandKind.RequestLine=22` は、`ProcessingLineKind` の `CoreMetal`、`Steel`、`CoreWood`、`BowGear` の1本を依頼する命令である。場所は `EconomyTargetKind.Region` と `RegionId`、または地図クリックのセル `Cell` で指定する。戦術 JSON は次の形とし、`region` は数値の区域 IDである。

```json
{"type":"economy","kind":"RequestLine","line":"Steel","region":3}
```

参謀の大・小モデルは同じ `line` 語彙を使い、名前表の自軍区域を `region` に変換する。「北の鉱山から鋼のラインを作って」のように地点名が来た場合は、名前表でその資源地点を含む区域が一意に決まるときだけ変換する。決まらなければ命令を作らない。

#### 自動配置と却下

シミュレーションは命令を受けた時点で文明・時代・対応する資源地点・初期木材を固定順に確認する。通れば既存の自動管理ラインへ依頼地点を記録し、次の内政周期から指定地点に近い資源を優先して、鉱山または木材所、精錬所、炭焼き小屋、製鋼所、弓具所とベルトを既存の自動配置規則で段階的に建てる。ラインの `LineManager` は `Automatic` のままであり、依頼だけでは手動ラインにならない。

失敗時は資源・建物・木材を変更せず、`EconomyLineRejected` をタイムラインへ記録する。理由は `LineUnavailable`（文明・時代・機能または既存ラインの都合）、`LineResourceMissing`（資源地点なし）、`LineWoodShortfall`（木材不足）、`LinePlacementUnavailable`（合法な建設地点なし）である。依頼の位置とライン種別もイベントの位置・値に含める。

#### 人向け画面・検証

EconomyPanel の Toolkit の Build タブに「ラインを頼む」項目を置く。ライン種別を選んでから地図をクリックすると、区域表があれば区域依頼、区域表がなければセル依頼を既存の Economy command port へ送る。設計図の保存・貼り付けとは別の操作である。

評価用の fake staff response と `eval-interpreter` は `RequestLine` と `line` を通常の EconomyCommand と同じように採点する。テストでは、命令なしの診断ハッシュ不変、指定位置に近いライン、却下理由、記録・再生ハッシュ、fake staff response、戦術 JSON の読み取りを確認する。シミュレーション層は UnityEngine に依存せず、場所選択・並び順・イベント順は固定順である。

### 32.32 ラインを守る・断つ（V3-6 follow-up）

#### 決めたこと

お任せのラインを敵が壊したときも `LineManager` は `Automatic` のままにする。ただし、建物またはベルトが壊れた tick を起点に、同じラインの再構築を `LineRebuildDelayTicks` tick 遅らせる。待ち時間中は不足したベルトを置かず、手運びも止めるため、ラインの流れは止まる。再構築可能時刻はラインごとに持ち、同じ tick の複数の破壊は一つの待ち時間へまとめる。既定値は 0 で、従来どおり次の AI 周期に直せる。

| 値 | 既定値 | Terrain マップ | 意味 |
|---|---:|---:|---|
| `EconomyRules.LineRebuildDelayTicks` | 0 | 200 | 敵に壊されてからお任せが直し始めるまでの tick 数（20 tick/秒） |
| `EconomyRules.RaidLinePriority` | 0 | 1 | 0 は従来の村人→建物→ベルト、1 以上はラインの建物・ベルトを先に選ぶ |

`RaidLinePriority` が有効な地形では、襲撃兵は射程内のライン建物・ベルトを通常の村人・建物より先に選ぶ。見張り塔と城も、ラインを攻撃目標にしている敵兵を、同じ射程内の他の敵兵より先に撃つ。値が 0 のマップでは襲撃と塔の既存の選択順を変えない。距離、建物／ベルトの種類、ID の比較は固定順で行い、Dictionary 列挙や壁時計は使わない。

Contracts の enum・view・イベント型は増やさない。ライン切断は既存の `EconomyLineRejected` に `CommandId = ulong.MaxValue` を持つ内部イベントとして記録し、表示側で「ライン N が切断された（作り直しまで X 秒）」と表示する。これは既存のライン依頼却下と区別でき、リプレイにも同じイベントが現れる。

#### 決定論と互換性

`LineRebuildDelayTicks` と `RaidLinePriority` は Simulation 側の `EconomyRules` に置く。値が 0 の場合、新しいクールダウン状態は正規状態へ書かないため、既存マップの状態ハッシュは変わらない。Terrain マップだけ値を有効にし、その設定は `ScenarioBinary` の末尾の長さを持つ任意 tail に保存して記録・再生で一致させる。新しい値を有効にした Terrain マップでは、設定ハッシュと破壊後の状態ハッシュが変わる。

#### 検証

待ち時間 0 の既存ライン、待ち時間 200 の Terrain ライン、20 tick 間隔の襲撃、ライン切断イベント、塔のライン防衛、記録・再生の全 tick ハッシュを `Processing`、`Raid`、`Belt`、`Industry`、`Determinism` のフィルターで確認する。UnityEngine を Simulation 系へ参照させず、シーン・Prefab・`.meta` は変更しない。

### 32.33 時代1からの兵・時代の時計・見えた敵の文明（2026-10-10）

測定（お任せどうし、今のゲームの設定、20分）：時代1に約10分、時代2には20分でも届かず、兵は歩兵だけだった。弓兵・騎兵は時代2からで、歩兵が最適だからではなく、作れる段階に届いていなかった。オーナー決定で次の3つを入れた。どれも旗の下で、旗オフは今までと同じ。`LiveGameRules`（全文明）でオン。

**旗 `EarlyArms`（拡張欄 ID 15、#376）**
- 時代1から、文明ごとに歩兵以外を1種類訓練できる。弓兵＝冶金・森林・工兵・教団・山岳・都市、軽騎兵＝農耕・石工・隊商・騎馬・学府・漁労・関所・聖地（`Simulation.Training.cs` の `EarlyArmsUnit`）。騎兵（`Cavalry`）は金属が要り、時代1では多くの文明が作れないので、軽騎兵にした。重い騎兵・破城槌は時代2からのまま

- 時代は tick 4800（4分）・10800（9分）・15600（13分）に、資源も条件も無しで進む（`AdvanceByAgeClock`）

**見えた敵の文明（a/enemy-looks）**

**旗 `PushWaves`（拡張欄 ID 18）：後半の押し込みを波にする（2026-10-12）**
- 問題：`SiegeByAge` の後も、12分以降に立っている兵が両陣営 3〜12 体しかいなかった。訓練は続いているが、出た兵が1体ずつ前線へ歩いて順に倒されていた
- 押し込みが始まったら（開始条件は今までと同じ `latePushLatched`：8分以降の優勢、時刻、または時代3）、陣営ごとに3つの状態を繰り返す（`Simulation.LatePush.cs` の `PushWaveState`）
  1. 集結：自分のコアから敵のコアへの経路上 `WaveStagingDistance`（25 m）の点に全軍を集める。新しく訓練された兵もここへ来る
  2. 突撃：立っている兵（村人・斥候を除く）が `WaveSize`（24）に達するか、`WaveMaxWaitTicks`（2400＝2分）待って `WaveMinSize`（6）以上いれば、全軍でコアへ。突撃中も、近くに敵の兵がいればそれと戦う（コアを攻撃するのは兵の目標が無いとき）

- 時代2のうちは攻城の倍率が低いので、突撃は削られて引く。時代3で決着する
- 人（`Human`）・戦術（`Tactic`）の命令がある軍団は波に入らない。戦術の命令は波の命令より優先する
- 波の状態が変わるたびに時系列へ `AiReport`（`Value`＝状態、`CommandId`＝突撃を始めたときの兵の数）を1行出す。Contracts は変えていない

- 途中の失敗（記録）：(1) 波を時代3まで止めたら、13分まで戦いが無くなった。(2) 突撃中に敵の兵を無視させたら、両軍がすれ違ってコアを殴り合うだけの競走になり、西が8戦全勝した。(3) その前の試み（旗 `ArmyMuster`、不採用）は「新しい兵を10体まとめてから出す」だけで、全軍が突っ込み続けるので増えなかった

### 33.7 段階3その2の決定と測定（2026-10-16）

#### 中盤の数値からの原因

終端だけでなく、CraftTree3オンの `measurements_20261016e` の tick 15,600・18,000・20,400を読む。seed 3では、tick 15,600のBridgeがFrames 0 / ArmsKit 0 / CutStone 22、CaravanがFrames 32 / ArmsKit 0 / Charcoal 0で、組立所も無かった。tick 18,000でもCaravanはFrames 69 / ArmsKit 6 / Charcoal 0、tick 20,400でもScholarly 0 / SiegeParts 0 / Mechanism 0であり、研究・加工の入力不足が原因だった。

一方、seed 1のMountainはtick 18,000にAssembler・Blacksmith、Frames 69、Scholarly 4、Charcoal 47を持ち、終端までにScholarly 10/5（生産/消費）、Mechanism 1/1、Scholarly研究使用4になった。seed 2のBridgeはtick 18,000にSiegeWorkshop・Assembler、Frames 75、ArmsKit 9、Scholarly 9、Charcoal 26を持ち、SiegeParts 8、Mechanism 4、Scholarly 14を生産した。seed 8のMetropolisもtick 18,000にSiegeParts 8、Mechanism 1、Scholarly 2を持ち、終端でSiegeParts 9/1、Mechanism 1/1、Scholarly 2/2になった。研究開始イベント自体は既存パックに無いため、研究への投入は `scholarlyUsedResearch` / `mechanismUsedResearch` で読む。

#### 今回の決定

- `ScenarioEconomy.SiegePartsStockLimit` を追加し、既定値を8とする。AssemblerのSiegePartsは在庫8で止める。
- CraftTree3のお任せ破城槌上限を「基礎上限＋SiegeParts在庫」とし、在庫があれば次の破城槌へ使えるようにする。
- レシピ選択は、時代3研究の有無、Scholarly / Mechanismの不足、SiegeWorkshopの有無、SiegeParts在庫上限を数値条件にする。研究が開いているときはScholarly不足ならScholarly、ScholarlyがあればMechanismを選ぶ。研究が無いときは研究用商品を選ばない。
- ScholarlyがありMechanismが無い状態で研究を開始できる場合は、Mechanismを先に作るため研究投入を保留する。Lv2加工建物は建物ID順に1つを選び、Mechanism 1個でLv3へ上げる。
- ID 43の拡張欄はVersion 2・19整数へ更新する。Version 1・18整数は読み込み、`SiegePartsStockLimit` は既定値8で補う。

#### 追加テスト

`CraftTree3Tests` に、(1) SiegeParts在庫で自動破城槌上限が上がり訓練時に消費される、(2) 開いた研究に対してScholarlyの後にMechanismを作る、(3) 時代3・Lv2加工建物をMechanismでLv3にする、の3テストを追加した。CraftTree3フィルターは11件合格・0失敗、Release Headlessビルドは警告0・エラー0だった。
