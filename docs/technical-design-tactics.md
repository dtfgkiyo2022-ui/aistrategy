# 技術設計：戦術＝プログラム（下書き、2026-10-06）

お任せの戦い方を、ユーザーが書いたプログラム（戦術）で差し替えられるようにする設計の**下書き**です。オーナー側の Claude が書きました。【】は仮の値、「未決」はオーナーの判断待ちです。企画書の書き換えはオーナーの確認のあとで行います（この資料だけでは企画書を変えません）。

ゲーム内 AI の3層（`technical-design-ai.md`）との関係は 9章にまとめます。矛盾したら、オーナーの決定が新しいほうを優先します。

## 0. オーナーの決定（2026-10-06）

- お任せの AI を「戦術＝プログラム」にする。ユーザーが Claude Code や ChatGPT で作った**戦術のリポジトリ**を、ゲームからフォルダを指定して読み込む。標準の戦術をゲームに同梱する
- 試合中の突発の判断は Jev／ローカル LLM。クラウドの API も使える
- 試合後の振り返りで戦術を直す、という循環を遊びの中心に置く
- 言語：標準は **JavaScript／TypeScript**（サンドボックスで動かす）。**Python は WebAssembly の箱**で動かす（機械学習のハードルを下げるため）。普通の Python は「自分の PC・自作の戦術だけ」で許す（環境変数を渡さない・警告を出す・共有できない）
- 機械学習：**学習はゲームの外**（Python の練習場＝ヘッドレスのシミュレーション）。試合での判断は、学習済みのモデル（データ）で行う
- 共有：Steam Workshop と GitHub 公開の両方。戦術どうしの対戦も入れる（＝それぞれ自分の戦術を使う人どうしの対戦。人が操作しない自動の対戦ではない、10-06 確認）。組みやすさは、手引き・チュートリアル・他人の戦術の改造で解決する（小さく始める必要はない）
- ユーザーに**ルールブック**と**試合の記録パック**（再生・時系列・発動した行・霧なしの振り返り）を見せる。見せる形には版番号を付ける
- 参謀の返事を会話らしくする案は、参謀の役割が変わるので保留

## 1. 全体像と、決めた芯（オーナー側の Claude の判断）

**芯：戦術はシミュレーションの外で動き、出力は今と同じ「命令」としてリプレイに記録される。** シミュレーションは戦術を呼ばない。

| 層 | 担当 | 呼ぶとき | 出すもの |
|---|---|---|---|
| 参謀（言葉） | Claude／OpenAI／Jev／ローカル LLM | 人が話しかけたとき | 命令、または**戦術の切り替え・つまみの変更** |
| **戦術（プログラム）** | ユーザーの JS/TS・Python（箱）・標準の戦術 | 【20tick】ごと＋出来事のとき | 命令（方針・内政・区域・全体方針） |
| 突発の判断 | Jev／ローカル LLM | 戦術が呼んだとき | 選択肢の答え（確信度つき） |
| 実行（決定論） | 今のお任せ AI・戦術 AI | 毎 tick | 移動・戦闘・内政 |

理由：
- **ロックステップを守る**：戦術は各プレイヤーの PC だけで動き、出した命令だけが同期される。相手の PC で自分の戦術を動かす必要がないので、**戦術の中身を相手に渡さずに済む**（秘密が守れる）。戦術の中で浮動小数点や時刻を使っても同期は崩れない
- **リプレイは命令の記録で再生できる**：戦術をもう一度動かさなくても、同じ試合が再現される（今の `ICommandPort.Propose` の経路と同じ）
- **1 tick ごとの兵の操作（毎 tick の `ITacticalDecision`）は戦術に開かない**。シミュレーションの中で動かすと、全員の PC で同じ戦術を決定論で動かす必要があり、秘密も速さも守れない。代わりに、命令の語彙（2.3）を豊かにして、細かい動きは決定論の実行役がこなす
  - 例：「部隊 3 は、損害が 3 割を超えたら拠点 B まで引く」は、命令に条件と予算を付けて実行役が守る（今の `LossBudget`・`EndCondition`）

## 2. 戦術の入出力（API）

### 2.1 呼ばれ方

- `onTick(view, memory)`：【20tick】（1秒）ごと。戦況を受け取り、命令の配列を返す
- `onEvent(event, view, memory)`：出来事のとき（接敵、拠点の喪失・奪取、時代の到達、部隊の壊滅、参謀からの切り替え）
- `onStart(setup)`：試合の始めに1回（地図の公開情報・自分の文明の候補・ルールの版）
- 返事が予算（4章）に間に合わなかったら、その回は**命令なし**。お任せの実行役が今の方針のまま続ける
- 戦術が例外で落ちたら、その試合の残りは**標準の戦術に切り替える**（理由を記録パックに残す）

### 2.2 戦況（view）

- 渡すのは、その陣営が観測できた情報だけ（技術ルール6）：`FactionObservation`（自軍・見えている敵・接触・目標・襲撃先）、自陣の `EconomyView`、区域の一覧、文明と時代、資源
- 形は**版番号つきの JSON 互換の木**（数値は整数か小数。Fix64 はそのまま渡さず、決まった桁の小数に直す）。版を上げても古い戦術が動くよう、項目は足すだけにする
- `memory`：戦術が次の回へ持ち越せる自由な値（大きさ【64KB】まで）。試合をまたぐ記憶は 7章の別の仕組みにする

### 2.3 命令（出力）

今ある語彙をそのまま使う。新しい命令の種類は、ルールブックに載せてから足す。

- 方針：`PolicyOrder`（`PolicyKind`・目標・優先度・損害の予算・終わりの条件・予備の割合）
- 内政：`EconomyCommand`（建てる・訓練・村人の割り当て・ライン・研究・交易・時代を進める・お任せへ戻す など）
- 区域の担当、全体方針（maintain／concentrate／none、`ReturnToAuto`）
- `judge(question)`：Jev／ローカル LLM への問い合わせ（非同期。答えは次の回の `view.answers` に届く）。費用は予算のメーターに数える
- 命令はすべて `CommandSource.Ai`（戦術を表す新しい値を足すかは未決）として、観測した tick と失効の条件を付ける。**人の命令が優先**

## 3. 決定論とリプレイ

- 同期とリプレイに必要なのは命令の記録だけ（1章）。**戦術の中は決定論でなくてよい**。小数の推論が PC ごとにずれても、返事が遅れて命令が抜けても、変わるのは「自分の PC がどの命令を出したか」だけで、同期は崩れない
- 戦術は壁時計の予算で動かす（返事を待ってシミュレーションを止めない）。遅い PC では命令の抜ける回が増える
- **戦術どうしの対戦は「人＋戦術」どうしの普通の対戦のこと**（2026-10-06 オーナー確認）。人が操作しない自動の対戦（どの PC でも同じ結果を求めるもの）は作らない。そのため、計算量で予算を数える仕組みは要らない（入れるかは T-2 の作りやすさで決める）

## 4. サンドボックス

| 実行環境 | 言語 | 封じ込め | 予算の数え方 | T-0 の結果 |
|---|---|---|---|---|
| **Jint**（.NET の中の JS） | JS／TS（TS は事前に JS へ変換） | .NET の型を渡さない設定で、ファイル・ネットに届かない | 文の数・再帰の深さ・メモリ・時間 | S1：**IL2CPP の製品版で `System.Runtime.CompilerServices.Unsafe` 6.0.0 が足りずビルド失敗**。DLL の入手はオーナーの許可待ち |
| **CPython WASI**（wasmtime） | Python（標準ライブラリのみ） | ファイル・環境変数・ネット・プロセスすべて封じた | 燃料（計算量）・メモリ・時間 | S2：起動 0.1 秒、1回 0.09ms。標準ライブラリのフォルダが書き込めるので、試合ごとに写しを渡す |
| **Pyodide**（Deno の中） | Python＋numpy | Python 側・js 経由の脱出もすべて封じた（権限は pyodide のフォルダの読み取りだけ） | 時間だけ（燃料がない） | S3：起動 2.1 秒、numpy の判断 0.013ms。Deno が約 93MB |
| 普通の Python | 何でも | 封じない（自作・自分の PC だけ。共有不可・警告） | 時間 | — |

- 標準は **Jint**（同じプロセスで動き、起動が速い）。S1 が通ることが前提
- Python は、**numpy が要らなければ CPython WASI、要るなら Pyodide**
- 予算（普通の試合）：1回【5ms】、1秒あたり【10ms】。超えた回は命令なし。続けて【10】回超えたら標準の戦術へ
- 封じ込めの試験（T-0 の S1〜S3 で書いた脱出の試験）は、製品の CI に入れて毎回確かめる

## 5. 戦術のリポジトリの形

```
my-tactic/
  tactic.json        名前・作者・版・言語（js/ts/python-wasi/pyodide）・入口・API の版・説明
  main.js            または main.ts / main.py
  models/            学習済みのモデル（データ）
  README.md          何をする戦術か（共有のとき表示）
```

- ゲームは `tactic.json` の API の版を見て、合わなければ読み込まずに理由を出す
- 戦術は**データとコードだけ**。外部のパッケージは、同梱できる純粋な JS／Python に限る（npm・pip を試合中に取りにいかない）
- 標準の戦術は、今のお任せ AI（`PolicyDecision`・`OffenseDecision`・`EconomyDecision`）と同じ動きを JS で書いたものにする。**今のお任せ AI は消さず、戦術が失敗したときの土台として残す**（企画書4章）

## 6. 機械学習

- **学習はゲームの外**：ヘッドレスのシミュレーション（S5：12000tick が普通の地図 18 秒、16 並列で約 3000 試合/時）を Python から回す「練習場」を配る。形は Gymnasium に似せる（`reset`・`step`・観測・報酬）。中身は今の CLI を子プロセスで動かす
- **試合では学習済みのモデル（データ）だけ**を使う。推論の方法（S4）は**まず B で始める**（2026-10-06 オーナー決定）：
  - **B（採用）**：サンドボックスの numpy で推論（Pyodide。追加の依存なし、S3 で 0.013ms。モデルは `.npz` などの重みで渡す）。Python（Pyodide）の戦術だけが使える
  - A（後で）：ONNX Runtime を同梱（`.onnx` をそのまま読める。DLL のダウンロードの許可と IL2CPP の試作が要る。Unity Inference Engine は ONNX の変換がエディタ専用で、製品版でユーザーの `.onnx` を読めない）
  - C（後で）：小さな推論器を C# で自前に書く（全結合・活性化だけ。依存なし、JS からも呼べる）
  - JS の戦術からもモデルを使いたい声が出たら、A か C を足す。どれを選んでも同期には影響しない（3章）

## 7. 共有と安全

- Steam Workshop と GitHub の両方。読み込むのは**フォルダ**で、どこから来たかは問わない（サンドボックスで守る）
- 共有された戦術は、サンドボックスの中だけで動く。普通の Python の戦術は共有できない（読み込むときに「自作か」を確かめる）
- 戦術に渡さないもの：API キー、環境変数、ファイル、ネット。Jev／LLM への問い合わせは、ゲームが代わりに送る（キーは戦術に見せない）
- 試合をまたぐ記憶：戦術のフォルダとは別の、ゲームが管理する小さな保存領域【1MB】。共有のときには入れない

## 8. ユーザーに見せるもの

- **ルールブック**：戦況の項目・命令の語彙・ルールの数値（版番号つき）。戦術を書く人と、Claude Code／ChatGPT に読ませる資料を兼ねる。コードの定義から自動で作る
- **試合の記録パック**（版番号つき）：リプレイ、時系列、**どの回にどの命令を出したか（戦術の行）**、霧なしの振り返り、戦術の失敗・時間切れの記録。Claude Code に渡して「どこを直すか」を相談できる形にする
- 手引きとチュートリアル：標準の戦術を少しずつ改造していく形

## 9. 参謀・突発の判断との関係

- 参謀（`technical-design-ai.md`）は、言葉を命令に直す役は残し、加えて**戦術の切り替えと、戦術が公開したつまみ（攻める時刻・守りの厚さ など）を変える**役を持つ。会話らしい返事の案は保留（0章）
- Jev／ローカル LLM は、戦術から `judge` で呼ぶ関数になる。費用の表示と予算のメーターは今の設計どおり

## 10. 段階（それぞれ Codex に発注、案）

| 段階 | 作るもの | 完了の目安 |
|---|---|---|
| T-0 | 試作（実行環境の封じ込めと速さ） | S1（Jint の IL2CPP）が残り。S2〜S5 は済 |
| T-1 | 戦況の JSON（版つき）と命令の語彙の JSON、検証。C# で書いた偽の戦術で、今の `Propose` の経路から命令が出る | 偽の戦術で試合が決着し、リプレイが一致する |
| T-2 | Jint の実行環境（予算・例外・標準へのフォールバック）。標準の戦術を JS で書く（今のお任せ AI と同じ動き） | 標準の戦術同士の試合が、今のお任せ同士と同程度に決着する |
| T-3 | 戦術のフォルダの読み込み（`tactic.json`）、ゲーム内の選択画面、CLI の `--tactic` | ヘッドレスで「戦術A 対 戦術B」を回せる |
| T-4 | 試合の記録パック（8章） | 記録パックを Claude Code に渡して、直す所を相談できる |
| T-5 | Python（CPython WASI、次に Pyodide）。練習場（Gymnasium 風） | Python の戦術が動き、練習場で学習したモデルを試合で使える |
| T-6 | ルールブックの自動生成、手引き、Workshop／GitHub の読み込み | 他人の戦術を読み込んで改造できる |
